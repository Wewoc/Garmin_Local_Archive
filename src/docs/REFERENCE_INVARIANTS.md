# Garmin Local Archive — REFERENCE_INVARIANTS

Module- and feature-specific invariants. Core architecture invariants
(sole-write-authority overview, layer separation, locking principle,
bootstrap order) live in [`GLA_GUIDELINES.md`](GLA_GUIDELINES.md) —
this file is the per-module detail, to consult when that specific
module is being touched.

Pure rules, not session history or rationale — for the reasoning behind
a given rule, see `CHANGELOG.md`.

---

## Security / Token

- `garmin_security.py` — `cfg` is imported lazily (local import inside each function); sole owner of `garmin_token.enc` and `garmin_token_log.json` (events: `created`/`invalidated`/`blocked`/`valid`; `valid` is serialized compactly, all others with `indent=2`; the `caller` field reads `GARMIN_SESSION_LOG_PREFIX` directly from `os.environ`, not via `cfg`)
- `garmin_security.py::has_unresolved_mfa_block()` — fails open on a read error; `garmin_api.py::login()` blocks headless SSO until a genuine SSO login clears the block (a manual token reset does NOT clear it)

## Normalization / Schema

- `CURRENT_SCHEMA_VERSION = 4` in `garmin_normalizer.py`
- `garmin_import.py::parse_day()` — `user_summary.restingHeartRate` is the export's value of the day (`currentDayRestingHeartRate`), an absent day value stays empty and never falls back to the 7-day average; the average is kept as `user_summary.lastSevenDaysAvgRestingHeartRate`, never inside `heart_rates` (v1.7.5.7)

## Dashboards / Layouts

- `dash_layout.py` + `dash_layout_html.py` + `reference_ranges.py` — passive resources, no I/O
- `dash_encryptor.py` — sole owner of the HTML encryption logic, Leaf Node
- `dialogs.py` — shared `PasswordConfirmDialog`, imported by `panel_archive` and `panel_outputs`
- The mirror password is never stored in Windows Credential Manager — always entered manually
- `reference_ranges.py` — imported by specialists, never by plotters
- `dash_autosize.py` — auto-size boundary calculation, Leaf Node; `compute_autosize_bounds()` + `autosize_note()`
- `dashboards/custom_dash_builder.py` — builds an in-memory specialist object (`types.ModuleType`) at runtime, deliberately not named `*_dash.py` (so `dash_runner.scan()` doesn't pick it up as a real specialist); `dash_runner.build()` accepts any object with `.META`/`.build()`/`.__name__`
- `app/garmin_dashboard_presets.py` — sole owner of `~/.garmin_dashboard_presets.json`
- `theme.py` — single source of truth for all app/dashboard color tokens; six built-in themes (`_THEMES` dict), active one read from settings (`active_theme` key, GUI dropdown in Settings tab). Falls back to Theme 1 if the key is missing or invalid. `dash_layout.py` and `layouts/render/live.py` both import `theme` directly — the only place `layouts/` breaks its otherwise strict independence from `app/`.

## App Layer / GUI

- `app/panel_chat.py` — Ollama chat panel, uses `clients/ollama_client.py` via a lazy-import helper, never at module level
- Settings tab: two columns — `PanelSettings` on the left (fixed 400px), action panels on the right (flexible)
- `scheduler/daily_update.py` — GUI-free; a `sys.path` root anchor is set before the first project import; every further project import is lazy (after the environment is configured)
- `APP_VERSION` comes from `version.py` — never kept in sync manually elsewhere
- `frozen_paths.py` — sole source for frozen-path resolution (`scripts_root()`, `add_to_path()`, `doc_path()`, `is_t3_standalone()` — v1.7.2.4, `is_t2_standard(reference_file=None)` — v1.7.2.4-Nacherweiterung), Leaf Node in `src/`. Does NOT cover `garmin_app.py`/`garmin_app_standalone.py`'s own `script_dir()`/`script_path()`, nor `dash_runner._load_plotters()` or `dash_plotter_html_complex.py`'s `render/` loader
- `log_utils.py` — domain-less Leaf Node in `src/`; `with_timestamp(log_fn)` prefixes log-callback messages with a timestamp
- `process_status.py` (v1.7.2.4) — sole source for "is process X running" where there's no port to probe (GUI, `daily_update.exe`) via a fixed PID-lock-file under `Path.home()` + `ctypes`/`OpenProcess` liveness check; also the sole `is_mcp_running()` (TCP probe), which `app/panel_mcp.py::_mcp_server_is_running()` delegates to rather than duplicating. Leaf Node in `src/`, with a documented exception (`garmin_config` imported lazily for `MCP_HTTP_PORT` — see `REFERENCE_GARMIN.md § Documented Exceptions`)
- `updater.py` (v1.7.2.4) — sole source for T3 self-update logic (GitHub release asset resolution, download+SHA256-verify+extract). Leaf Node in `src/`, stdlib only, no project imports at all. Fails closed: refuses to apply an update whose release publishes no checksum, rather than applying it unverified
- `export/backfill_source_backup.py` — imports `SETTINGS_FILE` from `garmin_app_settings` instead of hardcoding it independently — the sole source for the settings path in the project

## Build

- `build_manifest.py::HIDDEN_IMPORTS_COMMON`/`HIDDEN_IMPORTS_T3_EXTRA` — single source of truth for PyInstaller hidden imports; T2 = COMMON, T3 = COMMON + T3_EXTRA. `embed_dest(subfolder)` in `build_standalone.py` — the sole source for `--add-data` destination-path logic
- `sqlite3` / `_sqlite3` are in `HIDDEN_IMPORTS_COMMON` (T2 and T3 — `mcp_sql` needs them in the frozen package); `array`, `bisect`, `dataclasses`, `tempfile` are in `HIDDEN_IMPORTS_T3_EXTRA` because the bulk modules import them. Pinned by `tests/test_build_output.py` (v1.7.6)

## Mirror / Container

- `garmin_import_mirror.py` — sole owner of the mirror-import operation; orchestrates only, never writes directly (raw via `garmin_writer`, context via `context_writer.write_file()`, quality via `_upsert_quality()`); its local `_QUALITY_RANK` copy is deliberate (not imported from `quality/_maint`; must be kept in sync manually if labels change)
- `garmin_container.py` — sole owner of `mirror.gla`
- The container sections are `quality_log`, `raw`, `summary`, `context`, `source`, `bulk`, `bulk_source` (the last two since v1.7.6.2); the order of the older sections in a container is unchanged
- `normalize()` is never called during mirror import — raw data inside the mirror is already normalized
- Import pauses the background timer (same as Bulk Import)
- Container keys use POSIX forward slashes (`rel.as_posix()`)
- `mirror.gla` is written atomically: `mirror.gla.tmp` → `fsync()` → `os.replace()`
- The password for `lock()` may optionally be stored in Windows Credential Manager (user's choice); the password for `unlock_meta()`/`fulfill_order()` is always entered manually
- `mirror.gla` itself may be stored anywhere (any path, any medium) — only the relative paths read *from* an opened container are constrained: each one must resolve inside `base_dir` before anything is written; a path that would escape it aborts the whole import (fail-closed, v1.7.4.3)

## Source / Quality / Backup

- `garmin_source_quality.py` — sole owner of source-quality assessment, Leaf Node. Derives `intraday_present` from the raw API response; freeze-when-present strategy (intraday data already present is never overwritten by a degraded response); `assess_source_from_file` distinguishes "absent" from "unreadable"; `compare_source` returns `skip_warn` on unreadable. The `force=True` parameter overrides the whole decision table and forces `"write"` — exclusively for the deliberate Force-Refetch path, never for a normal sync
- `garmin_source_writer.py::write_source()` / `garmin_collector.py::_fetch_and_assess()` — both forward `force: bool = False` through to `compare_source()`; `_fetch_and_assess()`'s `force` cannot be applied separately afterwards, since `write_source()` is called internally
- `garmin_backup.py::backup_raw()` / `garmin_backup_source.py::backup_source()` — `force: bool = False` parameter, forwards `{filename}` as `force_filenames` to `_consolidate_raw_months()`/`_consolidate_source_months()`; the replace scope is always per filename, never per month (prevents collateral damage to other already-good days consolidated in the same monthly archive). the consolidation always runs against today's real calendar month, not the written day's own month (`force=True` since v1.7.4.0.4, every call since v1.7.5.6) — otherwise the same consolidation step skips that month as "current" and the replace never happens
- `garmin_backup.py::backup_quality_log()` refuses to overwrite a monthly snapshot with a log whose day count is less than half the existing snapshot's (v1.7.4.0.4 data-loss guard)
- `quality._io._load_quality_log()`'s `integrity_warnings` (unreadable file, checksum mismatch, unparseable entry date) is recomputed fresh on every call, not accumulated or cached — a warning source must live inside this function itself, never in a caller's local variable, or it silently disappears on the next independent call (e.g. the Archive Info panel's own refresh) (v1.7.4.0.4, "Variante B")
- `garmin_collector.py::main()` rejects a negative `GARMIN_MAX_DAYS_PER_SESSION` with a named error instead of silently treating it as anything else (v1.7.4.0.4) — only `0` means "unlimited"
- `garmin_collector.py::run_import()`'s downgrade protection uses the same `_check_downgrade()` rule as the normal sync, for every source — not just `source == "api"` (v1.7.4.0.4)
- `garmin_backup.py::_consolidate_raw_months()` / `garmin_backup_source.py::_consolidate_source_months()` — a file in the month folder is the newest backup copy of its day (`backup_raw()`/`backup_source()` overwrite it on every call) and replaces the same-named ZIP entry whenever its bytes differ; `force_filenames` only adds a replace of identical content. The scope stays per filename, never per month. Since v1.7.6.2.1 the rule lives once in `garmin_backup_common.consolidate_months()`; the two module functions are one-line calls to it
- `garmin_source_writer.py::patch_source_field()` backs up the patched `source/` file via `backup_source()` after a successful patch — lazy import, non-fatal, like `write_source()` (v1.7.5.6)
- `check_raw_stale_backups()`/`refresh_raw_backups()` and `check_source_stale_backups()`/`refresh_source_backups()` bring backup copies up to date that differ from their primary file: content-based (bytes of the month-folder copy, otherwise CRC32 and size of the ZIP entry), idempotent, never write to `raw/` or `source/`, never copy an invalid file over its backup, no quality-log marker (`garmin_backup_source.py` must not import pipeline modules). `garmin_collector.main()` runs them as step 3d before the login; any error is a warning (v1.7.5.6)
- `garmin_quality.py::touch_last_checked(data, days)` sets `last_checked` on the given days and nothing else — `quality`, `source`, `recheck`, `write`, `attempts`, `fields` and the log checksum stay as they are. It never saves: the caller holds `QUALITY_LOCK` from load to save and saves once after its loop. Its purpose is the MCP cache, which re-reads a day when `last_checked` differs from the cached value (v1.7.5.7)
- `garmin_repair_resting_hr.py` (v1.7.5.7, removable — every part carries the marker `RESTING-HR-REPAIR v1.7.5.7`) never writes a file itself: `raw/` + `summary/` through `garmin_writer.write_day()`, the quality log through `touch_last_checked()` + `_save_quality_log()` under one continuous `QUALITY_LOCK` hold, saved once after the loop. A caller that keeps its quality log in memory for the rest of its run passes it as `quality_data` — `garmin_collector.main()` does — because a log loaded by the repair is overwritten by the caller's next save and the marks are lost. Detection is by the content of `raw/` (no quality-log marker): the three-key import form of `heart_rates` without `user_summary.lastSevenDaysAvgRestingHeartRate`
- `GARMIN_RESTING_HR_REPAIR` is removed with `os.environ.pop()` when `garmin_collector.main()` reads it (step 3e); only the value `"1"` starts the repair. `scheduler/daily_update.py` only warns about unrepaired days and never stops the run, unlike the schema migration (v1.7.5.7)
- `garmin_track_migration.py` (v1.7.6.3, removable — every part carries the marker `TRACK-MIGRATION v1.7.6.3`) never writes a file itself: `raw/` + `summary/` through `garmin_writer` (`write_day()`, `rebuild_summary()`), the quality log through `touch_last_checked()` + `_save_quality_log()` under one continuous `QUALITY_LOCK` hold, saved once in a `finally`; a caller that keeps its quality log in memory for the rest of its run (`garmin_collector.main()`) must pass it as `quality_data`. A day is changed only when the coverage check passed (every non-empty field of an import-form section held by the bulk store with the same value; lists as the same entries in any order) and is checked again right before it is written; a day that fails stays untouched and the run goes on. Detection is by content, never by `source` in the quality log
- `garmin_migration_snapshot.py` (v1.7.6.3, removable) is the sole owner of `backup/migration/`: a ZIP of `raw/`, `summary/` and `log/quality_log.json`, written all or nothing (temp file, read-back check, `os.replace`) **before the first write of a migration run**; no valid copy, no write. The copy is not mirrored, not part of the silo check and never deleted by the app. The way back puts exact bytes back through `garmin_writer.restore_day_files()` and merges the quality-log entries of the restored days
- `GARMIN_TRACK_MIGRATION` is removed with `os.environ.pop()` when `garmin_collector.main()` reads it (step 3b2, before the schema migration and the resting heart rate repair); `"1"` migrates, `"preview"` only previews and ends the run before the login, any other value does nothing. `scheduler/daily_update.py` only warns with the number of days that can be migrated and never stops the run (v1.7.6.3)

## Bulk store (v1.7.6, extended v1.7.6.1)

- `garmin_bulk_writer.py` — sole owner of `garmin_data/bulk/raw/`, `garmin_data/bulk/aggregates/` (v1.7.6.1) and `garmin_data/bulk/source/`; the API sync never writes there, and it never writes `raw/`/`source/`/`summary/`. Day files, aggregates files and originals are written to `<name>.tmp` and moved with `os.replace` (retried up to five times on a lock); day files are flushed with `fsync`, originals are not. Originals are named by the SHA-256 of their bytes, never by a name from the export
- `BULK_SCHEMA_VERSION` is raised when the day format or the normalising rules change; the days are then written again from the originals. `garmin_health_map._BULK_MAX_SCHEMA` must equal it (pinned by `tests/test_broker.py`); the same holds for `AGG_SCHEMA_VERSION` of the aggregates files and `garmin_health_map._BULK_AGG_MAX_SCHEMA` (v1.7.6.1)
- A day is replaced only by a fuller one: same files and schema → nothing written; more files, or the same files with an older schema → written; fewer files or a set that is not a superset → kept; a day from a newer schema → kept. This holds for the aggregates files as well (`aggregates_status`, same comparison). A damaged day file counts as new; one that cannot be read for an I/O reason is `unreadable` and never replaced (the write answers `failed`; v1.7.6.1, F-1)
- `garmin_bulk_fit_reader.py`, `garmin_bulk_export_scanner.py`, `garmin_bulk_normalizer.py` — leaf nodes (stdlib only, no `garmin_config`). The reader rejects a file as a whole (`not_fit` / `truncated` / `crc` / `structure`), never half-read. No entry name of the export is returned, counted or logged. The normalizer plans a day only if both of its boundaries are known; a day with an unknown boundary gets no samples, nothing is guessed
- `garmin_bulk_import.py` — orchestrates only; no quality log, backup or API store. Originals are kept for the FIT types 32, 49, 44, 68, 58, 79 and 41 only. `dry_run=True` creates and writes nothing, not even folders. Never raises: an error ends in `summary["error"]` and `ok=False`
- `garmin_collector._bulk_phases()` and `_run_bulk_import()` remove `GARMIN_BULK_PHASES` / `GARMIN_BULK_DRYRUN` with `os.environ.pop()` when they read them (T3 runs `main()` in the GUI process); the GUI removes all three trigger variables (`TRIGGER_VARS`) after the run. An unknown phase selection starts nothing and counts as one failure. The `json` phase runs before `intraday`
- The import branch of `main()` writes a session log like a sync (`log/recent`, copied to `log/fail` on failure)
- Days written by the intraday phase are marked only through `garmin_quality.record_bulk_intraday()` (`entry["bulk"]["intraday"]` and `last_checked`), the daily values through `record_bulk_aggregates()` (`entry["bulk"]["aggregates"]`), under `QUALITY_LOCK`, saved once. Marks that failed are caught up (`catch_up_bulk_intraday()`/`catch_up_bulk_aggregates()`) at the end of an import and at the sync start (step 3f, `_run_bulk_mark_catch_up()`); a failure to mark or to save counts as a failure of the import run (v1.7.6.1, F-3). `entry["bulk"]` (a dict) is not `entry["source"] == "bulk"` (older JSON import, and the entries made for export-only days)
- `garmin_health_map._SERIES_TRACKS` — the first non-empty series of a day wins as a whole, a day is never mixed from two tracks; every intraday entry carries `series_source`; an unusable bulk day is skipped with one warning per day and process, never an exception
- `garmin_bulk_json_import.py` (v1.7.6.1) — orchestrates only; no quality log, `raw/`, `summary/` or backup. The daily values go to `bulk/aggregates`, never to `raw/`; the JSON files of the export are kept as originals (`bulk/source/<xx>/<sha256>.json`). A day that is invalid or has too little data is rejected, reported and is not a failure of the run; `ok` is false only for what a rerun can mend. `dry_run=True` creates and writes nothing, not even folders. The summaries of the written days and the quality-log entries are made afterwards by `garmin_collector._finish_aggregates()` under `QUALITY_LOCK`
- Resolved summary (v1.7.6.1): `garmin_writer` is the only module that makes `summary/` from API data plus export data. For a day with an aggregates file, a key the API lacks or holds empty comes from the export as a whole, and a section that both hold as a dict is filled field by field, one level deep (v1.7.6.3, F-11: the API value stays when it is not empty, the export fills a field that is missing or `None`/`""`/`[]`/`{}`; `0` and `False` are values); `activities` keeps the whole-key rule; `raw/` never receives export values. An aggregates file that cannot be read → nothing is written and the writer answers `False` (a summary without the export's values must not replace a complete one); a missing, damaged or newer-schema file counts as none. Every caller evaluates the answer of `write_day()` / `write_summary_only()` / `rebuild_summary()` (F-4, F-5, F-6)
- `garmin_silo_check.py` (leaf) reads the file names in `bulk/aggregates`, `bulk/raw` and `bulk/source`, the marks of the quality log and — only for #9 — the `source_files` of the intraday day files and, since v1.7.6.2.1, the entry names of the ZIPs in `backup/bulk/source` (ZIP directories only): a day with an aggregates file is *export data* — its summary is not an orphan (#5) and, without `raw/`, is repaired from the aggregates (#7, `rebuild_summary()`). A day the quality log marks with `bulk.aggregates` whose file is lost is not an orphan either: the summary is the last copy of the resolved values and is never deleted for that reason (F-10, v1.7.6.2)
- Backup of the bulk store (v1.7.6.2): `garmin_backup_bulk.py` is the sole owner of `backup/bulk/` and only reads the store; `garmin_backup_common.py` (leaf, stdlib only) holds the monthly folder / ZIP flow it shares with the raw and source backups (since v1.7.6.2.1 both are thin shells over it). The originals have one ZIP per hash prefix that is never appended to: a new ZIP is written beside the old one, verified, swapped in with `os.replace`; a ZIP that cannot be read is left untouched and reported (`damaged_zips`). Nothing in the backup modules raises; at the caller a failed bulk backup is a warning (`_run_bulk_backup`, step 3g and after a bulk import), never a failed run
- Monthly backup ZIPs (v1.7.6.2.1): nothing is appended to or replaced in a ZIP that does not open or fails its check — it is left untouched, the month folder stays as the fallback and one error line names the ZIP; a ZIP a call began and could not finish is removed again. A source file the refresh cannot read counts as an error of the refresh. Every error line of the backup code carries the exception type and names the ZIP it is about; the traceback of an unexpected error goes to debug level. The append mode is not atomic (an interrupted append can damage a ZIP; the next run reports it)
- Mirror of the bulk store (v1.7.6.2): the container sections `bulk` (day files and daily values) and `bulk_source` (originals); `_classify_file()` is a fixed mapping, so a new folder is not mirrored until it is named there. The format version is unchanged and a container without the sections stays readable. `lock()` and `fulfill_order()` take an optional progress callback; a callback that raises never fails the operation
- Files come back into the bulk store only through `garmin_bulk_writer.import_day_file()` / `store_original()` (v1.7.6.2): the mirror import and the silo repair (#8/#9) never write a bulk file themselves. A container file is accepted only when `describe_container_path()` knows its name; an unknown name is skipped with a warning, never an error, and nothing lands outside the store. The bulk part of a mirror import runs before the raw days, so `write_day()` resolves their summary with the daily values
- A day that exists only as export data (quality log `write` false, no raw file in the container) is no error of the mirror import (F-8, v1.7.6.2): its summary is made from the daily values, its quality-log entry (label, fields, source of the other archive, `written` false) and its marks are made. `write` true without a raw file stays an error. The imported bulk files are backed up by the next sync start, not by the import
- Silo check and repair of the bulk store (v1.7.6.2): #8 `bulk_lost_intraday` / `bulk_lost_aggregates` (the quality log marks the day, the file is missing) and #9 `bulk_originals_missing` (a FIT original `bulk/source` lacks, named by an intraday day file or held by the backup) and `bulk_json_originals_missing` (a JSON original the backup holds and the store lacks) are restored from `backup/bulk` — #8 before #9, both before #3/#5/#7; no copy in the backup is an error (`no_backup`) and touches nothing else. The check notices a lost original through the intraday day files (FIT) and through the names in the backup (FIT and JSON; the `source_files` of an aggregates file are hashes of source entries, not of the JSON files): an original lost before it was ever backed up is not found unless a day file names it; a damaged day file is not detected
- Sources per day for the broker: `summary/` holds one resolved value per day; `raw_pct` fields (`sleep_*_pct`) read `raw/` and, for a day without a usable object there, `bulk/aggregates` (one source per day, never mixed); fields only the export has (`bulk_daily`, the four stress durations) read `bulk/aggregates`; `get_raw()` reads `raw/` only

## MCP Server / Proxy

- `clients/mcp_server.py`, `clients/mcp_health.py`, and `clients/mcp_context.py` are the only crossing points between the `clients/` world and the broker layer, via `maps/mcp_map.py` (v1.7.2.1 — `query_health()`/`query_context()` moved into their own files, each calling `mcp_map.query_health()`/`mcp_map.query_context()` on its own live branch) — no exception for internal-only consumers, even ones not registered as a tool
- `mcp_sql.py` is a pure SQLite data-access layer — no validation or bundle-resolution logic; that logic lives in `clients/mcp_health.py`/`clients/mcp_context.py` (v1.7.2.1 — moved out of the `mcp_server.py` wrapper) and, for `query_raw`'s `domain`/`field` check (v1.7.5.4), `clients/mcp_server.py` itself, plus the shared `clients/mcp_query_common.py` helpers
- SQLite is always a derived, reconstructible cache — never written independently, never a fourth data silo. `garmin_backup.py`/`garmin_mirror.py` do not need to know it exists; a lost or corrupt cache file forces a rebuild, not data loss
- `_route_query()` (`clients/mcp_query_common.py`, v1.7.2.1) is the single decision point every query tool passes through before branching into the SQLite or live-broker path
- `FIELD_UNITS` (unit annotations for `query_health()`/`query_context()`/`list_available_fields()`) is deliberately kept local to `clients/mcp_field_registry.py` (v1.7.2.1 — moved out of `mcp_server.py`), not placed in any `maps/` broker — the SQLite branch never reaches `mcp_map.py` today, so a broker-level unit source would currently be unreachable for any real request
- Raw-passthrough fields point to their processed counterparts from one table only: `RAW_FIELD_COUNTERPARTS` (`clients/mcp_field_registry.py`, v1.7.5.5) feeds both `resolve_health_field()`'s raw-field error and `query_raw()`'s `_meta.hint`. The raw field names are never copied into it — they come from `list_raw_fields("health")` — and `tests/test_mcp.py` checks every key against the registered raw fields and every counterpart against the real health fields
- The docstring of every MCP tool is its tool description: the MCP SDK exposes it as `description` — also for tools registered programmatically (`query_health = mcp.tool()(query_health)`) — and LLM clients choose and call tools from that text alone. It stays short and agent-facing (what the tool does, parameter formats, which sibling tool to use instead, real limits and result shape) and states the behaviour of the active SQLite path, including known limitations, never a promise that path does not keep. Session history, version numbers, internal module or file names and `NOTES_*.md` references belong in a `#` comment block above the function. Pinned by `tests/test_mcp.py` section 8a-ter (no internal references, at most 2000 characters, `query_raw` names exactly the registered raw fields, `get_archive_metadata` names exactly its nine kinds) (v1.7.5.1)
- `list_available_fields()["metadata_kinds"]` lists only the nine LLM-facing metadata kinds (`gateway_map.list_metadata_kinds(include_internal=False)`), never the five registered for the SQLite proxy's internal sync (`*_filenames`, `raw_file_hashes`, `context_resync_pending`) — `get_archive_metadata()` rejects those on the SQLite path (v1.7.5.1)
