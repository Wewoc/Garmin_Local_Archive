1. SETUP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Open the Settings tab. Three fields are required to get started:

GARMIN ACCOUNT
  Email       Your Garmin Connect login email
  Password    Your Garmin Connect password
              (stored in Windows Credential Manager, not in a text file)

DATA FOLDER
  Folder for the local archive — e.g. C:\Garmin\Data
  The folder is created automatically on first sync.

CONTEXT (location for weather and pollen data)
  Open Google Maps in your browser -> search your location
  -> copy the URL from the address bar -> paste it into
  the "Google Maps URL" field -> click "Set location".
  The app extracts latitude and longitude automatically.
  Without a location, no weather or pollen data will be archived.

Click "Save Settings" — the app is now ready for the first sync.

GDPR EXPORT (request now)
  For the complete history, request a GDPR export from Garmin —
  this can take several days, so request it now:
  -> https://www.garmin.com/en-US/account/datamanagement/
  Import: Settings -> Data Collection -> "Bulk Import"
  (details in Section 3)

-> For installation, Windows security prompts, and password storage
   details: README_APP.md.

2. FIRST SYNC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Click "Daily Sync" (big button at the top) to start the sync.
The sync downloads all days not yet in the archive,
starting from today and going backwards.

What gets downloaded:
  - Intraday data: heart rate, stress, SpO2, Body Battery
    (minute-level resolution)
  - Daily summaries: sleep, steps, HRV, ...
  - Weather and pollen data for your configured location

The log at the bottom shows progress.
The sync can be stopped at any time with "Stop" —
it will resume from where it left off on the next run.

-> For a full explanation of the Connection & Archive Status panel:
     see Section 12, "Connection & Archive Status".

If there are days with failed or incomplete downloads in the selected
sync range, a popup will appear before the sync starts: "Incomplete
records found: X days in the selected range — Refresh now?" Click
"Yes" to re-fetch those days, or "No" to skip them and sync normally.

Correction of the resting heart rate (v1.7.5.7): earlier versions of the
Bulk Import stored the 7-day average of the resting heart rate instead of
the value of the day. If your archive holds such imported days, a popup
"Data Correction - Backup Required" appears before the sync starts. It
names the number of days. What it does:
  - The correct value of each day is read from the saved Garmin original
    of that day (garmin_data/source/). Days without a saved original are
    named in the popup and stay unchanged.
  - The raw and summary files of those days are rewritten; the backup
    copies follow. The days are marked, so AI queries (MCP) show the
    corrected values after the next sync.
  - It takes a couple of minutes for a few thousand days and runs once:
    when no day is left to correct, the popup does not appear again.
Before you click "Yes", make a backup of your data folder (a copy of
garmin_data/ is enough). Click "No" to skip: nothing changes, and the
popup comes back at the next Sync Garmin. The scheduled Daily Sync never
stops for this; it only writes a note to its log ("N imported day(s) have
a wrong resting heart rate - open the app and run Sync Garmin once").
Imports made with v1.7.5.7 or later take the right value from the start.

Migration of the mixed archive (v1.7.6.3): earlier versions imported the
Garmin export into the same folder as the data from the Garmin API and
filled gaps in those files later. Such "mixed" days are made again from the
saved Garmin originals (garmin_data/source/); the export data stays in its
own folder (garmin_data/bulk/). If your archive holds such days, a popup
"Migrate / Preview only / Not now" appears before the sync starts. It names
the number of days. What it does:
  - A safety copy comes first: a ZIP of the folders raw/ and summary/ and of
    the quality log, in garmin_data/backup/migration/. It is checked right
    after it is written; if it fails, nothing is changed. The app never
    deletes these copies (about 25 MB for 2,900 days); delete old ones by
    hand when you do not need them any more.
  - Each day is made again from its saved Garmin original and then read
    back and compared. Days that the saved export does not fully cover
    (the log says "raw/ holds data that the bulk store / source/ does not
    reproduce") or that have no export data yet ("import the Garmin export
    first") are not touched and are named in the log.
  - The daily files are put together field by field: where Garmin's answer
    for an old day leaves a value empty (for example the lowest and highest
    heart rate), the export fills it. A few shown values change for migrated
    days: climbed floors follow Garmin's own value, six sleep durations
    differ by 0.01 hours, and the activity list of days from the earlier
    import is empty instead of wrong (it showed durations and distances a
    thousand and a hundred times too large).
  - It takes a couple of minutes for a few thousand days. The days are
    marked, so AI queries (MCP) show the corrected values after the next
    sync. It runs once: when no day is left, the popup does not appear again.
"Preview only" reports what would change, writes nothing, and the sync does
not run this time. "Not now" changes nothing; the popup comes back at the
next Sync Garmin. Before you click "Migrate", make a backup of your data
folder as well (a copy of garmin_data/ is enough). The scheduled Daily Sync
never changes your archive for this; it only writes a note to its log ("N
day(s) of the archive are still in the mixed form of the old export
import").
To put a safety copy back (Python needed, not part of the standalone app):
stop every sync, then in the source folder run
  python support-tools/archive-maintenance/restore_migration_snapshot.py --list
  python support-tools/archive-maintenance/restore_migration_snapshot.py --dry-run <name>
  python support-tools/archive-maintenance/restore_migration_snapshot.py <name>
Only files that differ are put back, byte for byte; days that are not in
the copy stay as they are. The migration is then offered again.
Days of the earlier import that have no saved Garmin original, and days
where the export differs from the stored data, are reported and left as they
are.

Rebuild of the daily values (v1.7.6.5): the Bulk Import keeps the JSON
files of the Garmin export (garmin_data/bulk/source/). Since v1.7.6.5 it
reads one more value from them, the training readiness score; days that
an earlier version imported do not have it yet. If your archive holds
such days, a popup "Rebuild / Preview only / Not now" appears before the
sync starts. It names the number of days. What it does:
  - The daily values of those days (garmin_data/bulk/aggregates/) are
    made again from the kept original files. The export itself (the ZIP)
    is not needed, nothing is downloaded and no login is used.
  - The Garmin API data (raw/), the original files and the other days
    stay as they are. The daily files in summary/ are written again (for
    now with the same content: the score is stored in the bulk folder and
    does not show in the daily files yet), and the days are marked so AI
    queries (MCP) read them again after the next sync.
  - No safety copy is made: the original files are not changed and the
    days can be rebuilt again at any time. The bulk folder is backed up
    at the end of the same sync start.
  - It takes well under a minute for a few thousand days (measured on
    one archive with 2,842 days: about 10 seconds for the daily values
    and half a minute for the daily files). It runs once: when no day is
    left, the popup does not appear again.
"Preview only" reports what would change, writes nothing, and the sync
does not run this time. "Not now" changes nothing; the popup comes back at
the next Sync Garmin. The scheduled Daily Sync does not show this popup and
does not rebuild. A day whose stored values are fuller than the kept
originals is left as it is, and the popup may come back at each start.
An older version of the app does not read the rebuilt files.

Large archives: if you have years of Garmin history, start with
`range` mode for the last 1–2 years before using `auto`. Downloading
everything at once can trigger Garmin rate limiting.

3. BULK IMPORT (GDPR EXPORT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For the complete history: request a GDPR export from Garmin.
  -> https://www.garmin.com/en-US/account/datamanagement/

The export arrives as a ZIP file (may take several days). The bulk
import reads your complete daily-summary history from it and, since
v1.7.6, the heart-rate series over the day.

Import:
  Settings tab -> Data Collection -> "Bulk Import"
  Choose "ZIP file" or "unpacked folder", then select it
  A dialog asks what to import:
    [x] Daily values (JSON)
    [x] Heart-rate series (FIT files)
  with the buttons Preview / Import / Cancel. Both parts are selected
  at first; you can import one or both.
  Duration: depends on archive size (minutes to hours)

Bulk Import and Daily Sync complement each other:
  Bulk Import provides the history, Daily Sync keeps it current.

Since v1.7.6.1 both parts are stored in garmin_data/bulk/, not in
`raw/`: `raw/` keeps only what came from the Garmin API. The daily
files in `summary/` are made from both — where a day has API data,
the API values win and the export only fills what is missing; a day
that exists only in the export gets its summary from the export.
Days that exist only in the export are marked `source: bulk` in the
quality log; the Background Timer asks the API for them within its
180-day window (Section 5).

Daily values (JSON) (v1.7.6.1):
  The daily values are stored in garmin_data/bulk/aggregates (one file
  per day), the JSON files of the export unchanged in bulk/source.
  - A day that is invalid or has too little data is skipped and listed
    in the log. This is not an error of the import (the same export
    would give the same result); the Background Timer may still get
    such a day from the API.
  - New for AI queries (MCP) and the dashboards: the time per day in
    the four stress zones (rest, low, medium, high), in seconds, from
    the export. The sleep percentages also work for days that exist
    only in the export.
  - A few values are defined slightly differently in the export and in
    the API (floors climbed, sleep duration by a few seconds, minimum
    and maximum heart rate and the stress block of the day). Where both
    exist, the API value is used.
  - The import is finished once the summaries, the quality log entries
    and the markers are made; if that fails, the import reports an
    error and running it again makes it good.
  - New in v1.7.6.7: the import also reads the health status of the
    day and the single pulse alerts and stores them with the daily
    values (no screen and no AI query shows them yet). Gear, personal
    records, saved courses and the zone files of the export are kept
    unchanged in garmin_data/bulk/source. A JSON file over 64 MB is
    skipped.
  - At the end of the import (and of the preview) the log lists what
    the export held: the number of files of each known kind, and the
    JSON files the app did not know, with the folders they lie in.
    File names are never written to the log.
  - If you import an export that you imported before, the days that
    gain a health status or a pulse alert are updated; all other days
    stay as they are. Run the preview first.
  - Running the same import again changes nothing.

Heart-rate series (FIT files) (v1.7.6):
  The export also holds the heart-rate curve over the day. It is stored
  in its own folder, garmin_data/bulk/ (one file per day, plus the
  unchanged FIT files of the export). Your existing daily files in
  raw/ and summary/ are not changed by this part.
  - AI queries (MCP) and the dashboards that show the heart-rate curve
    use these series for days that have no heart-rate series from the
    Daily Sync. A day the Daily Sync has is shown from the Daily Sync.
  - Preview: reads the export and reports what an import would do -
    files found, days new / changed / unchanged, number of samples.
    Nothing is written, and the background timer keeps running. The
    daily values have a preview too (v1.7.6.1).
  - Before an import starts, the app tells you that the folder
    garmin_data/bulk is part of the backup and the mirror (v1.7.6.2):
    the new files are backed up right after the import. Keep the
    export file as your fallback anyway.
  - Running the same import again changes nothing. Importing only part of
    an export (for example one inner ZIP) never replaces a fuller day.
  - Days that cannot be placed on a day (for example without a known day
    boundary) are listed in the log, not guessed.
  - The import writes a log like a sync does: log/recent/garmin_bulk_...
    (a copy goes to log/fail/ if it failed).

API CAPABILITY SCAN (optional)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Your Garmin account may provide more health data than the ~15 fields
synced by default — depending on which devices and features you use
(smart scale, blood pressure monitor, menstrual tracking, ...).

Settings -> Data Collection -> "API Scan" opens a dialog with three
actions:

Start Scan
  Checks which additional fields your account has actually used in the
  last few days (7 by default, adjustable). Nothing is archived during
  the scan -- it only detects which fields return real data.

Edit Config
  Shows only the fields the scan found. Enable the ones you want synced
  going forward. Each future Daily Sync then fetches them alongside your
  regular data.

Clear Config
  Resets the scan results (asks for confirmation). Your archived data is
  never affected.

Enabled fields with a recognized health value show up automatically in
Custom Dashboard. Your existing daily sync data and dashboards are
unaffected either way -- this is a purely additive, opt-in feature.

FORCE REFETCH (v1.7.1.7)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Daily Sync will not retry a day it already considers finished -- even
if that day's data is wrong or incomplete (e.g. a Bluetooth dropout
during sync). Force Refetch deliberately re-downloads a single day,
bypassing that protection.

Settings -> Data Collection -> "Force Refetch" opens a calendar dialog:

1. Select dates
   Click days to toggle them in/out. Each day's current quality is
   shown as a background colour (green = high, yellow = standard,
   red = failed).

2. Start
   Re-downloads each selected day from Garmin. Progress is shown live
   in a log window. Nothing is written to your archive yet.

3. Review
   Shows quality before/after and how many fields changed, per day.
   Confirm the days you want to keep, or reject them -- a rejected day
   is restored to exactly its previous state. Only confirmed days are
   written to your archive.

A safety copy of each day's pre-fetch data is kept automatically, so a
rejected day is never lost. "0 fields changed" in the review means
Garmin has nothing new for that day -- expected, not an error.

4. DASHBOARDS & ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Home tab: click the Dashboard dropdown (v) -> select a dashboard.
The dashboard opens directly inside the app window.

Available dashboards (selection):
  Health Analysis     HRV, RHR, SpO2, sleep, Body Battery,
                      stress — with personal reference values
  Timeseries          Intraday data as zoomable time series
  Heatmap             Six intraday metrics as time-of-day x date grids
  Daily Overview      All fields as an Excel table
  Health + Context    Health combined with weather/pollen
  Sleep Dashboard     Sleep phases, HRV trend, quality score

Live Tracking (v1.6.5): today's Body Battery, Heart Rate, Steps and Stress
plus last night's sleep summary — always current. Not part of the dashboard
list above; it refreshes automatically after every Daily Sync, or on demand
via the "Update Live" button (next to Daily Sync).
Takes about 30-60 seconds; progress shown in the log.

Files tab: Excel overview of all archived days (v).

Rebuild dashboards:
  Settings tab -> Outputs -> "Create All Dashboards"

Create Dashboards (Settings tab -> Dashboards) opens a popup with all available dashboards
and their output formats:

  Dashboard            HTML   Mobile HTML   Excel   JSON
  Timeseries             X        -           X       -
  Heatmap                X        -           -       -
  Health Analysis         X        X           -       X
  Daily Overview          -        -           X       -
  Health + Context        X        -           X       -
  Sleep & Recovery        X        -           -       -

Output is written to `BASE_DIR/dashboards/`. The folder opens
automatically after a successful build.

Export Data (Settings tab -> Dashboards -> "Export Data"):
  Writes your archive to external formats, separate from the HTML/
  Excel dashboards above. Per-adapter grid -- toggle Health/Context/
  Metadata independently for each format:

    Adapter    Format   Notes
    JSON       .json    Full archive, 1:1 broker output
    CSV        .csv     One row per day, wide format (health_<field>/
                         context_<source>_<field> columns) -- built for
                         Excel/LibreOffice. Intraday/series fields
                         excluded. Metadata in a separate file.
    InfluxDB   .txt     Full resolution incl. intraday/series data --
                         for garmin-grafana or similar tools.

  "Save & Add to Daily Sync" persists your selection and runs it
  automatically as part of every Daily Sync (see "Daily Sync button"
  below) -- no need to export by hand after each sync.

Intraday data — what the Timeseries dashboard shows:
The Timeseries dashboard renders every data point captured from the
API — no aggregation, no downsampling. The number of points per day
depends on what Garmin delivered at the time of sync:

  Metric          API resolution   Data points / day
  Heart Rate      ~1 minute        up to 1,440
  Stress          ~3 minutes       up to 480
  Body Battery    ~15 minutes      up to 96
  SpO2            ~1 hour          up to 24
  Respiration     variable         variable

Days with intraday data show full curves. Days without it — including
days from a GDPR bulk import — contain daily summary values only
(`standard` quality). The quality badge in
the archive panel shows the breakdown.

Custom Dashboard (free field selection):
  Settings tab -> Outputs -> "Custom Dashboard"
  Pick any Garmin and Context fields, set a date range
  (fixed dates or "days back"), choose HTML and/or Excel.
  Save the selection as a named preset to reuse it later.
  Optional: check "Encrypt" for a password-protected HTML
  output — same protection as Encrypted export below.

Encrypted export (for USB transport):
  Settings tab -> Outputs -> "Encrypted Dashboards"
  Enter a password (with confirmation) — never saved.
  Output: basedir/encrypted/ — files end in _enc.html
  Opens in any browser, decrypts locally, no internet needed.
  Mobile variants are not included. Not triggered by Daily Sync —
  encrypted export is always manual.

Dashboard tab (first tab): shows your HTML dashboards directly inside
the app — no browser needed. The Health Analysis dashboard loads by
default on startup. Use the dropdown at the top to switch between all
HTML dashboards in `BASE_DIR/dashboards/`. Fully interactive — zoom,
hover, and filter work exactly as in a browser.

Files tab (second tab): shows your Excel dashboards directly inside
the app — no Excel required. The Daily Overview spreadsheet loads by
default. Switch between files using the left dropdown and between
sheets using the right dropdown (appears automatically for multi-sheet
files). Chart sheets are hidden — only data sheets are shown. "Open
File" opens the selected file in whatever your system has registered
for `.xlsx` (Excel, LibreOffice, WPS). The file list refreshes
automatically after every dashboard build and on every tab switch.

The Health Analysis JSON includes a ready-to-use Markdown start prompt
(`health_garmin_prompt.md`) for Open WebUI / Ollama — load it as the
system prompt for AI-assisted interpretation.

The Health Analysis Mobile HTML is optimised for landscape phone
viewing — all metrics on one scrollable page, global range dropdown
(calendar weeks, months, fixed ranges) controls all charts at once.
Copy it to OneDrive or Google Drive to open on your phone.

The Sleep & Recovery dashboard shows HRV, Body Battery, and Sleep
duration alongside sleep phase composition (Deep / Light / REM / Awake
as %) and weather/pollen context. Tab 1 covers the full date range.
Tab 2 shows intraday detail for any selected day.

Reference ranges (Health Analysis) are based on published guidelines
(AHA, ACSM, Garmin/Firstbeat) — informational only, not medical advice.
Dashboard values from consumer wearables are indicative only — not
medical-grade.

5. BACKGROUND TIMER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Automatically repairs and fills your archive in the background while
the app is open — no manual intervention needed.

One time window matters here:

  180 days    The timer's retry window. The timer keeps retrying
              `standard`-quality or bulk-imported days within this
              180-day window, so that a day still has a real chance of
              being upgraded to full intraday quality.

Steps Backfill and Bulk Field Backfill (items 6 and 7 below) are
deliberate exceptions to this window — neither has an age limit. Bulk
Field Backfill closes a gap in what the official export format
contains in the first place, which has nothing to do with how old the
day is.

Start:
  Click "Timer: Off" -> set interval -> click "Start Timer"

The timer works through a priority queue each run:

1. Bulk Recheck (priority) — if you have imported a Garmin GDPR
   export, the timer first upgrades those days via the live API,
   oldest first, within the 180-day retry window described above.
   Runs exclusively until all candidates are resolved.
2. Repair — re-fetches days where the API call itself failed (no file
   created)
3. Quality — re-checks `standard` days where the previous day had
   intraday data and the retry window (180 days) is still open —
   worth trying again for a quality upgrade
4. Fill — fetches completely missing days between your earliest known
   date and yesterday
5. Source Backfill (v1.6.0.3) — if you were running GLA before
   v1.6.0.2, some historical days may be missing from the source
   archive. The timer fills this gap automatically, oldest first,
   within the 180-day retry window. Becomes a no-op once complete —
   runs invisibly in the background.
6. Steps Backfill (v1.6.3, no age limit since v1.7.3) — if you were
   running GLA before step count intraday support was added,
   high-quality days already in your archive may be missing this
   field. The timer adds it retroactively, oldest first — only a
   single lightweight API call per day, no re-fetch of everything
   else. No age limit: even years-old days can still recover this
   field. A day gives up after 2 failed attempts (so a day that genuinely never
   gets a steps value back is not retried forever). Becomes a no-op
   once complete.
7. Bulk Field Backfill (v1.7.3) — if you imported a Garmin GDPR
   export, the official export never contains a handful of fields at
   all — HRV, SpO2, Body Battery, respiration, training status, race
   predictions, max metrics — regardless of how old the day is (this
   is a gap in what the export format contains). Lowest priority, runs after everything
   else: the timer re-fetches each bulk-imported day once via the
   live API and fills in whichever of those fields it can, without
   ever overwriting data the export already had. A field gives up
   after 2 failed attempts, independently per field, so a field your
   device genuinely never recorded does not block the rest of that
   day or get retried forever. Becomes a no-op once every bulk day is
   either complete or has exhausted its attempts.

What the timer does while running, in short:
  - Checks for missing days and downloads them
  - Upgrades days that have no intraday data yet (as long as they are
    still within the 180-day retry window)
  - Retroactively adds newly supported data fields (like step count)
    to days already archived at full quality
  - Fills in the handful of fields the official Garmin export never
    contains for bulk-imported days, regardless of the day's age
  - Runs in the background without blocking the rest of the app

When all queues are empty the timer stops automatically and logs
"Archive complete".

Settings (shown next to the button):

  Field                  Default   Description
  Min. Interval (min)    5         Shortest wait between runs
  Max. Interval (min)    30        Longest wait between runs
  Min. Days per Run      3         Fewest days fetched per run
  Max. Days per Run      10        Most days fetched per run

The timer runs its own connection test before the first sync. If
successful, the connection indicators in the top panel turn green.
Clicking the timer button while a sync is running stops the current
download immediately.

The timer does not start automatically after restarting the app —
it must be activated manually each time.

Note: Export to Mirror automatically pauses the timer and restarts it
afterwards.

6. MIRROR / BACKUP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Mirror creates an encrypted backup of the complete archive
as a single .gla container file.

Setup:
  Settings tab -> Mirror target -> choose a path for the .gla file
  (e.g. Cloudspace\Backup\archive.gla or a USB drive)

Create backup:
  "Export to Mirror" — packs the archive into the container
  Enter a password and confirm it — always entered manually,
  never saved. Prevents silent storage of a mistyped password.
  The button opens a dialog with two options: "Export to Mirror"
  (create or update the backup) and "Import from Mirror" (restore
  data from an existing container). The button is greyed out if no
  mirror target is configured or the target is unreachable, and
  disabled automatically while a Sync or Context Sync is running.

Restore:
  "Import from Mirror" — unpacks the container into the archive
  Existing data is not overwritten if its quality in the archive
  is already higher than what the container provides
  (protection against regression).

Bulk folder (v1.7.6.2):
  The mirror container carries garmin_data/bulk (heart-rate series,
  daily values, the kept export files) and the import brings it back.
  Older containers stay readable; they simply have no bulk part. A day
  that exists only in the Garmin export is not an error on import.
  Mirror and import show progress in the log (every 10 % of the files,
  every section); with a large archive this takes minutes.
  The backup of the bulk folder (garmin_data/backup/bulk) is made by
  itself at the start of a sync and right after a bulk import. The
  first backup of a large export can take a while; a failure is only a
  warning and is tried again at the next start.

Damaged backup file (v1.7.6.2.1):
  The backups of your daily files (backup/raw, backup/source and
  backup/bulk) are kept as one ZIP per month. If such a ZIP cannot be
  opened or fails its check, nothing is written into it any more:
  it stays as it is, the new files wait in their month folder, and
  the log names the ZIP and the kind of error. The app does not
  repair a damaged ZIP by itself. Delete the damaged ZIP only while
  the daily files it was made from still exist: the backup of the
  bulk folder and the source backup make the missing copies again at
  the next sync; for the raw backup there is no automatic rebuild
  (see MAINTENANCE_GARMIN.md, "backfill_raw"). The mirror
  ("Export to Mirror") is a second copy of the whole archive.

7. AUTOMATED DAILY SYNC VIA WINDOWS TASK SCHEDULER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`daily_update` runs the full daily workflow headlessly — no GUI, no
manual interaction. Configure the app once, then let `daily_update`
handle the rest automatically via Windows Task Scheduler.

What it does on each run:
  1. Checks the archive for gaps — heals gaps up to 7 days automatically
  2. Syncs Garmin data for the missing period
  3. Syncs context data (weather, pollen, air quality)
  4. Rebuilds all dashboards
  5. Closes the console window if everything completed cleanly

Gaps larger than 7 days trigger a hard stop — open the app and sync
manually first.

Entry point per version:
  Standalone version:  daily_update.exe — double-click or Task Scheduler
  Standard EXE:        Starte_Daily_Sync.bat — double-click or Task Scheduler
  Scripts only:        python scheduler/daily_update.py

Setup in Task Scheduler:
  1. Windows key -> open "Task Scheduler"
  2. "Create Basic Task"
  3. Trigger: Daily, at your preferred time
  4. Action: Start a program
     Standalone: path to daily_update.exe
     Standard:   path to Starte_Daily_Sync.bat
  5. "Run with highest privileges" — not required

A ready-to-import XML template (`daily_update_task.xml`) ships in
`info/`. Import it once into Windows Task Scheduler. Recommended
settings:
  - Run daily in the morning
  - Enable "Run task as soon as possible after a scheduled start is
    missed" — ensures the sync runs after waking from sleep
  - Disable "Restart on failure" — prevents flooding `log/daily/` with
    error files

Console behaviour:

  State                          Behaviour
  All OK                         Console closes automatically
  Update available (default)     Stays open — yellow notice, open GitHub manually
  Update applied automatically   Console closes automatically (v1.7.2.4, see below)
  Update auto-apply failed       Stays open — red notice with the reason (v1.7.2.4)
  Error                          Stays open — red notice, check garmin_data/log/daily/
  Migration required             Stays open — open the app first (not if "Migrate data in Daily Sync" is on, see below)
  Settings missing               Stays open — open the app and save settings first

Automatic updates (v1.7.2.4, both versions): tick "Auto-apply
updates in Daily Sync" in Settings -> its own "Daily Sync" section. When
a new version is found, `daily_update` downloads, verifies, and applies
it by itself — no popup, nothing to click. If the app happens to be
open at that moment, it closes automatically (any unsaved changes in
open fields are lost) and does not reopen afterward. Off by default —
without it, `daily_update` behaves exactly as before (yellow notice,
open GitHub manually).

Data update in the daily sync (v1.7.6.4, both versions): after some
updates the app has to rewrite the summary files once (a "schema
update"). Normally `daily_update` stops with "Schema migration required"
and you open the app. Tick "Migrate data in Daily Sync" in Settings ->
its own "Daily Sync" section and it does the update by itself:
  - It first makes a safety copy of raw/, summary/ and the quality log
    (garmin_data/backup/migration/, a ZIP, checked after writing). This
    can take about a minute for a large archive. The log names the copy
    and the command that puts it back (restore_migration_snapshot.py,
    Python needed, not part of the standalone app; close the app first).
  - Without a checked copy nothing is changed: `daily_update` stops with
    the same message as when the setting is off.
  - The update itself runs inside the sync, before the login. Raw files
    are not touched, only the summary files are rewritten.
  - If the app is open it writes a warning to its log and goes on.
  - If some files are still outdated afterwards (for example a summary
    of a day that is not in the quality log), the log says how many and
    to open the app; the daily sync still counts as done, the exit code
    does not change. Every such run makes a new safety copy until the
    files are migrated.
  - The safety copies are not deleted by the app.
Off by default. With it off `daily_update` behaves as before.

Data update to schema 5 (v1.7.6.6): the daily summary files get a new
section "alerts" (pulse alerts, breathing disruption, load ratio, two body
battery levels, the stress rating of the day) and the section "training"
is filled for the first time. Because of that every summary file counts
as outdated once. The data update described above then runs once: in the
app (it asks for a backup first) or, with "Migrate data in Daily Sync"
ticked, in the next daily sync. Raw files are not touched and no Garmin
login is needed. Days that exist only in the Garmin export get the
training values that the export carries, but no alert values (the export
has none). If you use the MCP server (AI queries): its first start after
the update reads all days again, once. That takes longer than a normal
start and needs nothing from you; it does not matter whether the data
update or the server start comes first.

Prerequisite: the app must be configured at least once (email,
password, folder, location saved) before `daily_update` can run.
Running it before setup results in a hard stop with a clear message.

After updating the app: a fresh build occasionally causes Garmin to
reject the saved token on the next login, sometimes paired with a
step-up verification (MFA) — `daily_update` cannot resolve this
headlessly and will fail visibly. If a scheduled run fails right after
an update, open the GUI once and complete a normal login (entering the
MFA code if prompted). This re-establishes a valid token, and the next
scheduled run will succeed normally.

The headless sync writes a log to garmin_data/log/daily.

8. TROUBLESHOOTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Connection fails
  -> Check email and password
  -> Log into Garmin Connect in a browser (MFA may be required)
  -> Just try Sync Data / Connect again — a rejected or expired token
     is detected and cleared automatically, prompting a fresh login
     (with MFA if required). There is no separate "Reset Token" button
     anymore.

App asks for MFA code
  -> Enter the code from Garmin/email — it is saved afterwards

After app update: Garmin rejects the saved token
  -> Just reconnect / run Sync Data again — the app detects the
     rejected token and prompts a fresh login automatically
  -> (Garmin server-side security measure for new binaries)

Sync stops / no progress
  -> Read the log (bottom of the app or garmin_data/log/)
  -> Common cause: rate limit — wait a moment, then restart

Dashboard shows no data
  -> Run Daily Sync first
  -> Then click "Create All Dashboards" in Settings -> Outputs

Context data missing / no weather or pollen
  -> Settings -> Context: check the Google Maps URL
  -> Click "Set location" again — coordinates will be shown
     (lat / lon)
  -> Then run Daily Sync again
  -> If coordinates are correct but still no data:
     Open-Meteo API temporarily unavailable — retry later
  -> Context data is only loaded for days already in the archive
     (Garmin sync must run first)
  -> Data was fetched at the wrong location for some days (e.g. wrong
     Google Maps link, or a travel entry with the wrong dates)? Use
     "Context-Check" (Settings -> Data Management) to find and repair
     those days — see Section 12, "Buttons Reference".

Stress / Body Battery missing from Excel or dashboard
  -> Run `regenerate_summaries.py` once to rebuild all summary files
     from raw data.
  -> Standalone: use the "Silo-Check" button (Settings tab -> Data
     Management) to detect missing summaries, then click "Repair" to
     rebuild them automatically.

Background timer shows days as `standard` instead of `high`
  -> This is expected behaviour. `standard` means the API returned
     full daily data but no intraday detail (heart rate curve, stress
     curve, etc.). This happens for older dates where the API returned
     no intraday detail, or for device eras that never produced
     intraday data. The timer retries `standard` days
     only if the previous day had intraday data and the 180-day retry
     window is still open — after that the label is accepted as final
     and those days are never touched again.

Log shows errors but no data
  -> Check your email/password in Settings and make sure the data
     folder path is valid and writable.

-> For app-start problems, login/MFA issues, and password storage:
   README_APP.md, "Troubleshooting".

10. CHAT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Native chat panel, directly inside the app — no external tool required
for quick questions about your data. Formerly named "Ollama-Chat";
renamed to "Chat" in v1.7.2 when Cloud LLM support was added alongside
Ollama.

Two independent choices, made before Start:

  Backend
    Ollama       Local models run entirely on your own machine (an Ollama
                 cloud model -- name ending in "-cloud" -- is processed on
                 Ollama's servers instead). Requires Ollama installed and
                 running, plus at least one model pulled -- sizing guide
                 (rule of thumb: VRAM in GB minus 2 = usable model size) is
                 in README_APP.md, "Option A -- Built-in Chat".
    Cloud        Anthropic or OpenAI (v1.7.2). Requires an API key,
                 configured on the "MCP Server" tab (see Section 11) --
                 the key is stored in the Windows Credential Manager,
                 one entry per provider, never written to disk in
                 plaintext. Sends your questions and the data needed to
                 answer them to that provider's servers -- see the AI/
                 health disclaimer in README_APP.md for what that means.

  Source
    Summary (default)   Runs against your existing Health Analysis
                         export -- fast, no live query. Build one first:
                         Settings tab -> Dashboards -> "Create Dashboards", or
                         Outputs -> "Create All Dashboards" (Section 4).
    MCP tool-calling     (v1.7.2) The model queries your archive live via
                         the same MCP server external tools use (Section
                         11), for questions the daily snapshot alone
                         can't answer.

Using it:
  Open the "Chat" tab -> choose Backend and Source -> click "Start"
  For Ollama+Summary, the tab shows the age of your current Health
  Analysis export and a quick Ollama-reachability check before you
  click Start -- no request is sent until you do. If it shows "not
  found", the chat can still be started, but has no data to answer
  questions about.

  Once started: pick a model from the dropdown, type a question,
  press Enter or click Send. Larger models can take a while to
  respond -- a counter shows elapsed time.

  "Neuer Chat" clears the conversation and reloads context.
  Switching the model does the same automatically.

Streaming:
  Replies stream in as they're generated for every Backend/Source
  combination except Ollama + MCP tool-calling. Ollama's own streaming
  support for tool-calling is not yet reliable upstream (sourced,
  tracked upstream as ollama/ollama#12557), so that one combination
  waits for the complete answer instead of streaming it.

Chat History:
  Chat sessions auto-save as you go and can be reloaded later via the
  "Chat History" button, which lists past sessions by date/backend/
  model. A session using live MCP data can always be resumed. A session
  using the daily-summary snapshot can only be resumed if that snapshot
  hasn't changed since the session was saved -- otherwise it opens
  read-only (the underlying data has moved on, so continuing the
  conversation could produce inconsistent answers).

Troubleshooting:
  -> "Ollama: not reachable" -- make sure Ollama is running
     (ollama serve), then reopen the tab
  -> No models in the dropdown (Ollama) -- pull one first:
     ollama pull <model>
  -> "health_garmin.json: not found" -- no Health Analysis export exists
     yet; build one first (see "Using it" above), then reopen the tab
  -> Cloud backend greyed out / key not found -- configure the API key
     on the "MCP Server" tab first (Section 11)
  -> Errors during a chat appear directly in the chat window --
     no separate log file needed

11. MCP SERVER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Exposes your archive to local LLMs via the Model Context Protocol
(MCP) -- lets an MCP-compatible client (Claude Desktop, Open WebUI,
or similar) query your health and context data directly over
http://127.0.0.1:<port> (not reachable from other machines, by
design), without exporting files.

Using it (from the main app):
  Open the "MCP Server" tab -> choose LLM backend (ollama or cloud),
  set the port if needed -> click "Save Settings" -> click
  "Start MCP Server"

  cloud backend (optional):
    provider dropdown: Anthropic or OpenAI (v1.7.2) -- enter API key /
    model. The same key is also what the Chat tab's Cloud backend uses
    (Section 10) -- one entry per provider, configured here, not there.
    Note: the key is stored in the Windows Credential Manager, one
    entry per provider (v1.7.2) -- never written to disk in plaintext.
    Not re-loaded back into the field after saving.

  Headless checkbox (off by default): skips the server's own window
  entirely and runs it straight in the background -- for
  automation/scheduled use, not the everyday case. Takes effect on
  the next start, not the one already running.

  Extra allowed hosts checkbox (off by default): for MCP clients
  running inside Docker (e.g. Open WebUI) that need to reach the
  server as something other than 127.0.0.1/localhost. Unlocks a
  comma-separated field pre-filled with the common case,
  host.docker.internal, plus a line showing exactly what was
  recognized. Unchecking dims the field but keeps its content.

  If a server is already running, a dialog names the port it's
  already using instead of starting a second one.

Running without the main app:
  Standalone version:  mcp_server.exe
  Standard version:     clients/Starte_MCP_Server.bat

  Opens its own small window -- archive path, backend, port, the
  same Headless checkbox as above, and a live log. Useful for
  running the server on a machine or user session where the main
  app isn't installed.

  "Restart Server" in that window applies a changed archive path,
  backend or port without closing the window by hand -- the new
  process starts in the background, the window switches over
  automatically once it's confirmed running.

  Local cache: the server keeps a small local cache
  (sqlite/mcp_cache.db in your archive folder) so date-range
  questions ("how has my sleep been over the last three months")
  answer quickly even as the archive grows -- nothing to configure.
  It builds/updates itself automatically every time the server
  starts, so starting it after a long break may take a little
  longer than usual the first time. If your LLM client supports it,
  it can also ask the server to refresh the cache on demand -- useful
  right after a sync if you want the very latest data available
  immediately instead of waiting for the next restart.

  Baselines and anomalies (v1.7.5): your LLM client can ask "is
  anything unusual in my recent HRV/heart rate/sleep" -- this
  compares each day against your own personal 90-day average rather
  than a fixed medical threshold, and is recalculated automatically
  for the last ~140 days on every sync. If you ever correct or
  backfill health data from further back than that (rare), the
  affected days won't update on their own -- delete
  sqlite/mcp_cache.db and restart the server to force a complete
  refresh, same as for any other cache question above.

  Correlations (v1.7.5): your LLM client can ask whether two things
  move together over time -- "does pollen affect my HRV", "is my
  stress higher a few days before I sleep badly" -- across any
  combination of health and context fields, with an optional day
  shift for "does X today predict Y a few days later" questions.
  This is always computed fresh when asked, not cached, so it always
  reflects your latest synced data.

Don't have your own archive yet? A synthetic 180-day demo archive (ZIP
+ its own README, fictional data clearly marked as such) is available
from the project's GitHub repo under src/support-tools/demo-export/ --
not bundled with this app install. Point GARMIN_OUTPUT_DIR at it to try
the MCP Server without a real Garmin account.

For connecting Open WebUI or Claude Desktop to a running server, see
README_APP.md, "Connecting Open WebUI to the MCP Server".

12. BUTTONS REFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Quick reference for buttons not already covered in Sections 1-11.

Connection & Archive Status
  See Section 2, "First Sync", and the Archive info panel description
  there. Updated automatically before every sync; no manual test
  button.

Silo-Check
  Scans your data silos for inconsistencies the live pipeline does
  not catch — old gaps, interrupted runs, manual file operations, or
  import errors. Click "Silo-Check" to run. Read-only, completes in
  the background, runs silently at startup and takes a few seconds.
  Results appear in the log:
    "N days missing" — backup copies exist, click to restore
    automatically
    "N days missing, N no backup" — some days have no backup; a
    dialog lists them so you can re-fetch manually via Sync Data
  A day that exists only in the Garmin export (Bulk Import) is not
  reported as an orphan; if its summary is missing, the repair rebuilds
  it from the export data (v1.7.6.1).
  Bulk folder (v1.7.6.2): the check also reports bulk files that went
  missing ("#8 bulk files lost") and original export files that are
  gone ("#9 original export files missing"; since v1.7.6.2.1 also the
  JSON files of the export, found through the backup copies, and an
  original that is lost together with its day file). The repair
  restores them from garmin_data/backup/bulk; without a backup copy
  it says so, and
  the export file is the fallback. The daily file of a day whose bulk
  file is lost is no longer removed as an orphan.

Context-Check
  Same idea as Silo-Check, but for the context archive (weather,
  pollen, Brightsky, air quality) under Settings -> Data Management.
  Scans for missing days and for days whose stored location doesn't
  plausibly match your configured coordinates (e.g. after a wrong
  Google Maps link was used, or a travel entry in local_config.csv
  had the wrong dates). Read-only until you act on it.
  Results open in a dialog with collapsible sections. For a flagged
  day, click "Fix" and either paste a Google Maps link for the
  correct location or use the day's own suggested coordinates, then
  confirm. This re-downloads that day's data at the corrected
  location — it is a real re-fetch, not just a label correction,
  since a flagged day's underlying values were fetched at the wrong
  place to begin with.
  Note: for a day with no matching row in local_config.csv, the
  plausibility check compares its stored coordinate against your
  *current* Settings -> CONTEXT location, not the location that was
  active when that day was fetched. If you permanently relocate
  without adding a CSV row for the old period, previously-correct
  days from before the move will show up as "drift" afterwards — this
  is expected, not a data defect. Workaround: add a row to
  local_config.csv covering the old period (old coordinates, date_to
  = the day before the move) so those days keep being checked against
  the location that was actually correct for them — see "Sync Context
  / CSV" below.
  Note: if you use the Chat tab (MCP / live-archive mode) or an
  external MCP client, a just-repaired day may show no data for that
  source until the MCP server's next sync — either its next restart,
  or an LLM/MCP client explicitly calling its "refresh_cache" tool.
  This is expected; it prevents the old, already-known-wrong value
  from being served in the meantime.

Documentation
  Opens a dialog with three entries: Quickstart (first-time setup),
  User Guide (this document), and README App (installation/security).
  Each opens in a window inside the app (v1.7.6.4): README App is shown
  formatted (headings, tables, code), the other two as plain text.
  Links to web pages open in your browser. The window shows no pictures
  and has no search; you can keep it open next to the app and close it
  with "Close". If a file cannot be shown there, it opens in your
  default text editor or viewer as before.

Export Data
  Opens the per-adapter export popup — see Section 4, "Export Data",
  for format details. "Save & Add to Daily Sync" saves your current
  selection so it also runs automatically on the next Daily Sync.

Update (v1.7.2.4, both versions)
  Appears in the "new version available" popup alongside "Open GitHub"
  and "Dismiss". Downloads the new version, verifies it against a
  published checksum, and applies it. If verification fails, nothing is
  changed and the app keeps running as before. (v1.7.2.4.1) Standalone
  version: restarts itself automatically afterward, and if the new
  version fails to start, it's rolled back to the previous version
  automatically - no manual recovery needed. Standard version: applies
  the update and closes, same as before - start it again yourself to
  use the new version.

Auto-apply updates in Daily Sync (v1.7.2.4, both versions)
  Checkbox under Settings -> its own "Daily Sync" section. Saves
  immediately. When on, `daily_update` applies a new version by itself
  the next time one is found, instead of just showing a notice — see
  Section 7, "Automated Daily Sync", for what that looks like on a
  scheduled run. Off by default.

Migrate data in Daily Sync (v1.7.6.4, both versions)
  Checkbox under Settings -> its own "Daily Sync" section, below the
  auto-update checkbox. Saves immediately. When on, `daily_update` makes
  a safety copy and rewrites outdated summary files by itself instead of
  stopping with "Schema migration required" — see Section 7. Off by
  default; the app's own popup before a sync is not affected.

Sync Data / Stop
  Downloads missing days from Garmin Connect. Watch the log at the
  bottom for progress. First run may take a while depending on how
  far back you go.
  Standard: click Stop to cancel a running sync immediately.
  Standalone: click Stop to cancel — the current day finishes saving
  before stopping.

Sync Context / CSV
  Downloads weather and pollen data for your full archive date range
  — free, no account required. Weather data is fetched from
  Open-Meteo and Brightsky (DWD), pollen data from Open-Meteo Air
  Quality. Used by the Health + Context and Sleep & Recovery
  dashboards.
  Setting your location: Settings -> CONTEXT -> paste a Google Maps
  URL -> click "Set Location". The app extracts latitude and
  longitude automatically.
  CSV button: opens `local_config.csv` directly in Excel. Lets you
  define different coordinates for specific date ranges — useful if
  you travel or have relocated. Created automatically on first Sync
  Context. For a fixed home location, the Settings entry is
  sufficient.

Daily Sync button
  One-click daily workflow. Detects the gap since your last sync,
  then runs in sequence: Garmin Sync -> Context Sync -> Create All ->
  Export Data (only if a selection was saved via "Save & Add to
  Daily Sync" in the Export Data popup, Section 4) -> Live Tracking
  (fetches today's snapshot in the background, does not block or
  delay the steps above). If the gap is larger than 7 days a
  confirmation dialog appears before starting. The button is disabled
  while running.

Update Live button
  Fetches today's intraday data (Body Battery, Heart Rate, Steps,
  Stress) and last night's sleep summary, then refreshes the Live
  Tracking dashboard — without running a full Daily Sync. Takes about
  30–60 seconds. Also runs automatically after every Daily Sync — use
  this button to check in between.

Log: Simple / Log: Detailed
  Toggles the log output level in the GUI. Simple shows only key
  steps (default). Detailed shows every API call — useful for
  diagnosing connection issues or Garmin API changes. If you toggle
  while a sync is running, a yellow notice appears: "Takes effect on
  next sync." Session log files (in log/recent/ and log/fail/) always
  record at full detail regardless of this toggle.

Open Data Folder
  Opens your data folder in Windows Explorer.

Copy Last Error Log
  Copies the contents of the most recent error log from log/fail/ to
  your clipboard — ready to paste into a GitHub issue or support
  chat. Standalone: since there is no terminal, this is the primary
  way to retrieve diagnostic information when something goes wrong.
  If no error logs exist, a message appears in the log area instead.
